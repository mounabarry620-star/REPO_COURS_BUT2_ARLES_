Une image en mémoire : le tableau « à plat » CM diapo 25

On met les lignes bout à bout dans un seul tableau de width × height cases. Le pixel (x, y) est à l'indice t = y × width + x : on saute y lignes complètes, puis on avance de x.

Pourquoi un seul tableau ? Une seule allocation, un seul delete[], et surtout on peut écrire ou lire tous les pixels d'un coup avec write/read (les pixels sont rangés dans le même ordre que dans le fichier PGM).

La classe GrayImage CM diapos 26 et 28

class GrayImage { // N'oubliez pas <cstdint> !
  const uint16_t width, height; // dans [0;65535]
         uint8_t  *array;       // pixels dans [0;255]
  GrayImage() = delete;         // pas d'image sans taille
public:
  GrayImage& operator=(const GrayImage& b) = delete;
  GrayImage(uint16_t w, uint16_t h);
  GrayImage(const GrayImage& orig);
  ~GrayImage();
  inline const uint16_t& getWidth()  const { return width;  }
  inline const uint16_t& getHeight() const { return height; }
  inline uint8_t& pixel(uint16_t x, uint16_t y) {
    if (x >= width || y >= height)
      throw std::out_of_range("GrayImage::pixel : hors de l'image");
    return array[y * width + x];
  }
  inline const uint8_t& pixel(uint16_t x, uint16_t y) const { /* idem */ }
  ...
};
  • uint8_t : un pixel = exactement 1 octet, de 0 (noir) à 255 (blanc).
  • const sur les dimensions : la taille ne change jamais, donc on ne réalloue jamais le tableau.
  • = delete : une image sans taille n'a pas de sens ; et a = b changerait la taille de a, impossible car width est const.
  • pixel() renvoie une référence : on peut l'utiliser à gauche d'un =, ex. im.pixel(10,20) = 255;
  • La version const sert quand l'image est constante (ex. dans writePGM() const).

Constructeurs et destructeur CM diapo 27

GrayImage::GrayImage(uint16_t w, uint16_t h)
  : width(w), height(h), array(nullptr) // liste d'initialisation
{
  if (w == 0 || h == 0)
    throw std::invalid_argument("GrayImage : largeur et hauteur doivent être > 0");
  array = new uint8_t[size_t(width) * height];
}

GrayImage::GrayImage(const GrayImage& o) // copie PROFONDE
  : width(o.width), height(o.height), array(nullptr)
{
  array = new uint8_t[size_t(width) * height];
  for (size_t t = 0; t < size_t(width) * height; t++)
    array[t] = o.array[t];
}

GrayImage::~GrayImage()
{ delete[] array; }  // new[] -> delete[]

width étant const, on doit l'initialiser dans la liste après les « : » (impossible de l'affecter dans le corps).

  • Pourquoi new ? On ne connaît la taille qu'à l'exécution, et une image est trop grosse pour la pile (stack) : on la met sur le tas (heap).
  • On n'initialise pas les pixels : clear() ou readPGM() le feront.
  • size_t(width) * height : avec deux uint16_t, le calcul se fait en int et 65535 × 65535 déborde.

clear, rectangle et fillRectangle

void GrayImage::clear(uint8_t gray)  // gray = 0 par défaut (dans le .hpp)
{
  for (size_t t = 0; t < size_t(width) * height; t++)
    array[t] = gray;
}

void GrayImage::rectangle(uint16_t x, uint16_t y, uint16_t w, uint16_t h, uint8_t gray)
{
  if (w == 0 || h == 0) return;                  // rien à dessiner
  if (x + w > width || y + h > height)
    throw std::out_of_range("GrayImage::rectangle : le rectangle sort de l'image");
  for (uint16_t i = 0; i < w; i++) {
    pixel(x + i, y)         = gray;   // bord haut
    pixel(x + i, y + h - 1) = gray;   // bord bas
  }
  for (uint16_t j = 0; j < h; j++) {
    pixel(x,         y + j) = gray;   // bord gauche
    pixel(x + w - 1, y + j) = gray;   // bord droit
  }
}
// fillRectangle : même vérification, puis double boucle j (lignes), i (colonnes)
  • Le cadre occupe les colonnes x à x+w-1 : w pixels, pas w+1.
  • On vérifie avant de dessiner : on ne laisse pas un rectangle à moitié tracé.
  • x + w est calculé en int : pas de débordement.

Le format PGM « P5 » : l'exemple du TD1, octet par octet

  • L'en-tête est du texte ASCII : 0x50 = 'P', 0x35 = '5', 0x0a = LF (10), 0x20 = espace, 0x23 = '#'.
  • La largeur 5 est écrite avec le caractère '5' (0x35), pas l'octet 5.
  • Les pixels sont binaires : un octet par pixel, ligne par ligne, en commençant en haut à gauche.
x=01234
y=0025502550
y=1163264128255
y=212864128192128
y=3128128128128128

(Vérifié : notre readPGM relit exactement ces valeurs.)

Écrire un PGM : writePGM TD1 question 2

void GrayImage::writePGM(std::ostream& os) const
{
  // En-tête en texte ASCII (opérateur <<)...
  os << "P5\n"
     << "# Image sauvegardée par " << AUTEUR << " pour les TP de RepCod.\n"
     << width << " " << height << "\n"
     << 255 << "\n";
  // ... puis les pixels en binaire, d'un seul bloc (CM diapo 20).
  os.write((const char*)array, size_t(width) * height);
  if (!os)
    throw std::runtime_error("writePGM : erreur d'écriture");
}
std::ofstream ofs("tp1_rectangles.pgm", std::ios::binary); // binary !
im.writePGM(ofs);
  • << pour l'en-tête : il écrit le nombre 320 sous forme de texte « 320 » (3 caractères). C'est ce que veut l'en-tête.
  • write pour les pixels : il recopie les octets tels quels. Avec <<, un pixel 200 deviendrait le texte « 200 ».
  • write attend un const char* et un nombre d'octets : on convertit le pointeur avec (const char*).
  • Le paramètre est un std::ostream& : la même fonction écrit dans un fichier, dans std::cout ou dans un stringstream.
  • Le fichier doit être ouvert avec std::ios::binary (CM diapo 9), sinon Windows transforme chaque octet 10 en 13,10.

Lire l'en-tête : skip_line et skip_comments TD1 questions 3 et 4

// Lit des caractères jusqu'au « Line Feed » (inclus).
void skip_line(std::istream& is)
{
  char c;
  while (is.get(c) && c != '\n') {}
}

// Lit un caractère : si c'est '#', on saute la ligne
// et on recommence ; sinon on le remet sur le flux
// avec putback(), comme s'il n'avait jamais été lu.
void skip_comments(std::istream& is)
{
  char c;
  while (is.get(c) && c == '#')
    skip_line(is);
  if (is)
    is.putback(c);
}

is.get(c) renvoie le flux : il vaut « faux » en fin de fichier, ce qui évite une boucle infinie (le while (c != '\n') des notes boucle pour toujours si le LF n'arrive jamais).

Le piège de chat.pgm

L'en-tête de chat.pgm contient des commentaires après les dimensions :

320 240⏎
# Encore du bordel⏎
# après les dimensions⏎
# de l'image.⏎
255⏎

is >> w >> h s'arrête juste avant le ⏎ rouge. Appelée tout de suite, skip_comments lit ce ⏎, voit que ce n'est pas '#' et le remet : aucun commentaire sauté, et is >> maxval échoue sur '#'.

Solution : is >> std::ws (saute espaces, tabulations, CR, LF) avant skip_comments(is). Marche aussi avec les fins de ligne Windows et un en-tête sur une ligne (PGM.txt : « be as lenient as possible »).

Lire un PGM : readPGM TD1 question 5

GrayImage* GrayImage::readPGM(std::istream& is)
{
  std::string magic;
  is >> magic;              // lit "P5"
  if (magic != "P5" && magic != "P2")
    throw std::runtime_error("readPGM : ce n'est pas un fichier PGM");
  is >> std::ws;            // saute les blancs (LF, CR, espaces)
  skip_comments(is);
  unsigned int w = 0, h = 0;
  if (!(is >> w >> h))
    throw std::runtime_error("readPGM : largeur et hauteur illisibles");
  if (w == 0 || h == 0 || w > 65535 || h > 65535)
    throw std::runtime_error("readPGM : dimensions invalides");
  is >> std::ws;            // saute le LF laissé par >>
  skip_comments(is);
  unsigned int maxval = 0;
  if (!(is >> maxval))
    throw std::runtime_error("readPGM : valeur maximale illisible");
  if (maxval != 255)
    throw std::runtime_error("readPGM : seul 255 est géré");
  GrayImage* res = new GrayImage(uint16_t(w), uint16_t(h));
  if (magic == "P5") {
    is.get();   // UN SEUL caractère blanc après 255
    is.read((char*)res->array, size_t(w) * h);
  } else {      // "P2" (bonus) : pixels écrits en décimal
    for (size_t t = 0; t < size_t(w) * h && is; t++) {
      unsigned int v = 0;
      if (is >> v && v > 255)
        is.setstate(std::ios::failbit);
      res->array[t] = uint8_t(v);
    }
  }
  if (!is) {    // fichier tronqué ou corrompu
    delete res; // on libère avant de signaler l'erreur
    throw std::runtime_error("readPGM : pixels incomplets ou invalides");
  }
  return res;
}
  • On lit w et h dans des unsigned int pour pouvoir vérifier qu'ils tiennent dans un uint16_t.

readPGM : les deux questions à savoir expliquer

Pourquoi readPGM est static ?

Une méthode normale s'appelle sur une image qui existe déjà (im.writePGM(f)). Or c'est justement readPGM qui fabrique l'image : il faudrait une image pour créer une image, « le serpent qui se mord la queue » (TD1).

Avec static, la fonction est attachée à la classe :

std::ifstream f("images/chat.pgm", std::ios::binary);
GrayImage* im = GrayImage::readPGM(f);  // pas d'objet avant
...
delete im;  // c'est l'appelant qui libère

Elle reste membre de GrayImage : elle a le droit d'écrire dans res->array, qui est privé.

Pourquoi un seul is.get() après 255 ?

PGM.txt : « only a single character of whitespace (typically a newline) is allowed after the maxval ».

Si on sautait tous les blancs (avec >> ou un skip_comments qui saute les espaces), les pixels 10 et 32 seraient avalés : l'image serait décalée et il manquerait des octets à la fin. Avec chat.pgm, ça arrive vraiment (des pixels valent 10).

Questions possibles au contrôle

  1. Où est le pixel (x, y) dans array ? À l'indice y × width + x.
  2. Taille du fichier PGM d'une image 320 × 240 ? En-tête (quelques dizaines d'octets) + 320 × 240 = 76 800 octets de pixels.
  3. Pourquoi ios::binary ? Pour éviter les conversions de fin de ligne (CM diapo 9) : sinon des octets 10 ou 13 peuvent être modifiés.
  4. Pourquoi write et pas << pour les pixels ? << écrit du texte (« 200 » = 3 octets), write écrit l'octet 200.
  1. Pourquoi readPGM est static ? Elle crée l'image : on ne peut pas exiger qu'une image existe déjà pour l'appeler.
  2. Que fait putback(c) ? Il remet le caractère c dans le flux : la prochaine lecture le relira.
  3. Pourquoi interdire operator= ? Les dimensions sont const : a = b ne peut pas changer la taille de a.
  4. Pourquoi un constructeur de copie ? La copie par défaut copierait le pointeur : deux images partageraient le même tableau, puis deux delete[].
  5. Après 255, combien de blancs ? Exactement un (PGM.txt). Le premier pixel peut lui-même valoir 10 ou 32.
